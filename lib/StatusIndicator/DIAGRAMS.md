# StatusIndicator Library - Code Linkage Diagrams

This document explains the various code linkage diagrams generated by Doxygen for the StatusIndicator library.

## 📊 Generated Diagram Types

### 1. **Class Collaboration Diagrams**
- **File**: `classStatusIndicator__coll__graph.svg`
- **Purpose**: Shows relationships between classes and the types they use
- **Shows**: How StatusIndicator class collaborates with enums (IndicatorMode, StatusType, LEDType)

### 2. **Call Graphs** (`_cgraph.svg`)
- **Purpose**: Shows which functions a specific function calls
- **Examples**:
  - `update()` → calls various `update*()` methods based on mode
  - `begin()` → calls `setupPWMChannels()` and `setMode()`
  - Convenience methods → call `setStatusWithMode()`

### 3. **Caller Graphs** (`_icgraph.svg`)  
- **Purpose**: Shows which functions call a specific function (reverse call graph)
- **Examples**:
  - `setLEDColor()` ← called by various animation update methods
  - `setSingleLED()` ← called by animation methods for single LED boards
  - `setMode()` ← called by initialization and convenience methods

### 4. **Include Dependency Graphs**
- **Files**: `StatusIndicator_8h__incl.svg`, `StatusIndicator_8cpp__incl.svg`
- **Purpose**: Shows header file dependencies
- **Shows**: 
  - StatusIndicator.h includes Arduino.h
  - StatusIndicator.cpp includes StatusIndicator.h

### 5. **Include Dependents Graph**
- **File**: `StatusIndicator_8h__dep__incl.svg`
- **Purpose**: Shows which files depend on this header
- **Shows**: StatusIndicator.cpp depends on StatusIndicator.h

## 📋 Key Insights from Diagrams

### 1. **Modular Design**
- Clear separation between single LED and RGB LED handling
- Animation logic separated into individual update methods
- Hardware abstraction through enum types

### 2. **Function Dependencies**
- `update()` is the main orchestrator calling appropriate animation methods
- Hardware-specific methods (`setLEDColor()`, `setSingleLED()`) are called by multiple animation methods
- Color conversion (`hsvToRgb()`, `getStatusColor()`) provides RGB support

### 3. **Initialization Flow**
- `begin()` → `setupPWMChannels()` → `setMode(OFF)`
- Constructor sets up pins based on LED type detection
- Hardware detection influences the entire call chain

### 4. **Control Flow**
- User calls convenience methods (`showNormal()`, `showError()`, etc.)
- These call `setStatusWithMode()` which sets both status and mode
- `update()` must be called regularly to execute animations
- Animation methods handle both RGB and single LED cases

## 🛠 Diagram Customization

The diagrams can be customized by modifying the Doxyfile:
- `UML_LOOK = YES` - Enables UML-style class diagrams
- `CALL_GRAPH = YES` - Enables function call graphs
- `CALLER_GRAPH = YES` - Enables reverse call graphs
- `DOT_IMAGE_FORMAT = svg` - Generates scalable vector graphics
- `INTERACTIVE_SVG = YES` - Makes diagrams clickable

These diagrams provide a visual understanding of the code structure and help identify:
- Function dependencies and call patterns
- Architectural relationships
- Potential refactoring opportunities
- Code complexity and coupling
